# 주간 시간표 후보 비교 API

## 호출 순서

1. 재직 중인 학교 관리자가 기존 엑셀 검증 API에 `forGeneration=true`를 추가한다. 학기가 있으면 `POST /api/v2/terms/{termId}/load-imports/validate?forGeneration=true`, 학교 설정 단계면 `POST /api/v2/school/load-imports/validate?academicYear=2026&forGeneration=true`를 사용한다. multipart의 파일·시트·별칭·셀 오류 규격은 [시수표 API](../sql/m1-load-import.md)에 있다.
2. 검증 성공 시 기존 JSON에 `validatedLoadId`(UUID)가 추가된다. 서버는 정규화된 시수를 Redis에 30분간 보관한다. 기본 검증 요청은 기존과 동일하게 동작한다.
3. 해당 ID로 아래 API를 호출한다. 반환값은 이번 요청의 비교용 주간 배치다. 재호출은 새 탐색을 시작한다. 학기·주간 시간표·날짜별 기록에 쓰기는 발생하지 않는다.

| 상황 | POST 경로 | 허용 검증본 |
| --- | --- | --- |
| 학기 생성 후 | `/api/v2/terms/{termId}/schedule-candidates` | 동일 학교·학기의 검증본 또는 해당 학교·학년도의 학교 설정 검증본 |
| 최초 학교 설정 | `/api/v2/school/schedule-candidates?academicYear=2026` | 동일 학교·학년도의 학교 설정 검증본 |

두 경로 모두 기존 인증 헤더와 `Content-Type: application/json`을 사용한다. 생성 시점에 학교 소속, 관리자 재직 상태, 명부, 교시 설정과 등록된 교사 불가 교시를 다시 조회한다. 요청 본문에는 시수와 교사·과목·반 조합을 직접 전달할 수 없다.

## 요청·응답 예시

엑셀 검증본에 교사 10의 과목 20, 학급 30이 주 1차시로 등록되어 있다고 가정한다. 월·화 1교시 중 월요일을 희망하면 두 후보의 점수가 달라진다.

```json
{
  "validatedLoadId": "375d0754-c375-42c6-b1f0-f630a9693e37",
  "teachingSlots": [{"day":"MON","period":1},{"day":"TUE","period":1}],
  "preferences": [{"teacherId":"10","kind":"WANT","anyOf":[{"day":"MON","period":1}]}]
}
```

```json
{
  "validatedLoadId": "375d0754-c375-42c6-b1f0-f630a9693e37",
  "status": "READY",
  "stopReason": "SEARCH_EXHAUSTED",
  "detail": null,
  "elapsedMs": 3,
  "candidates": [
    {
      "candidateId": "f272c7729cf053f271960dbfd917341c814e459f59460f539905c9493c810941",
      "score": {"wantsMet":1,"wantsTotal":1,"teachersWithNoWantMet":0,"avoidsMet":0,"avoidsTotal":0},
      "placements": [{"teacherId":"10","subjectId":"20","classId":"30","slot":{"day":"MON","period":1}}]
    },
    {
      "candidateId": "1c620aaccf23c450bdbd3cd478b852e251c61ac0633d25677ed958351dbfed26",
      "score": {"wantsMet":0,"wantsTotal":1,"teachersWithNoWantMet":1,"avoidsMet":0,"avoidsTotal":0},
      "placements": [{"teacherId":"10","subjectId":"20","classId":"30","slot":{"day":"TUE","period":1}}]
    }
  ]
}
```

`day`는 MON~SUN, `period`는 학교 설정의 교시 번호다. `teachingSlots`를 생략하면 월~금에 등록된 모든 교시를 연다. 요일별 단축 수업은 실제 편성할 교시만 지정한다. 동일 요일에 사용하려는 교시의 실제 시각이 겹치면 학교 설정을 복구하도록 요청한다.

`preferences`는 선택 입력이다. 한 교사가 “월 1 또는 화 2”를 원하면 `WANT` 한 건의 `anyOf`에 두 교시를 넣는다. 둘 중 한 번이라도 수업이 있으면 1건 충족이다. `AVOID`의 묶음은 한 교시 이상 비면 충족한다. 각각 비워야 한다면 한 교시씩 별도 묶음으로 전송한다. 순서만 다른 동일 묶음은 한 번만 집계한다. 희망 미제출자는 영 건 충족 교사 수에서 제외한다. `teacher_availability`에 등록된 실제 불가 시간은 모든 후보에서 배제한다. 후보 순위는 **희망 충족 건수 내림차순 → 희망이 하나도 반영되지 않은 교사 수 오름차순 → 기피 충족 건수 내림차순**이다. 동점 후보는 배치 해시순으로 정렬한다.

## 상태와 오류

| HTTP | 상태 또는 오류 | 클라이언트 동작 |
| --- | --- | --- |
| 200 | READY | 후보 1~4개를 표시한다. TIME_LIMIT이면 제한 내 발견한 상위 안이다. |
| 200 | INFEASIBLE | 후보 0개. CAPACITY이면 detail의 교사·학급·셀을 확인한다. SEARCH_EXHAUSTED이면 가능한 배치를 모두 배제했다. |
| 200 | TIME_LIMIT_NO_SOLUTION | 후보 0개. 자료와 실제 수업 불가 조건을 검토한다. 배정 불가능이 입증된 상태와 구분한다. |
| 400 | 필수 ID, JSON, 교시, 선호 형식, 입력 크기 오류 | 응답 메시지에 따라 요청을 수정한다. 주간 교시 최대 128개, 배당 행·주간 차시 각각 최대 8,192개, 선호 묶음 최대 2,048개다. |
| 403 / 404 | 재직 관리자 권한 없음 / 학기 또는 사용 가능한 검증본 없음 | 소속·권한을 확인하거나 원본을 다시 검증한다. 다른 학기와 만료 검증본은 같은 404다. |
| 409 | 해당 교사·과목·반의 명부 변경 또는 학교 교시 설정 오류 | 명부·교시를 수정하고 엑셀을 다시 검증한다. |
| 503 | GENERATION_BUSY / LOAD_PREVIEW_UNAVAILABLE | 실행 중이면 Retry-After(2초) 후 재시도한다. 임시 저장소 장애면 복구 후 재시도한다. |

종료 사유 TOP_FOUR_AT_BOUND는 서로 다른 네 후보 모두 선호 지표의 이론상 최고점에 도달한 경우다. SEARCH_EXHAUSTED는 점수 상한 가지치기를 포함한 탐색이 완료되었다는 뜻이다. 후보 ID는 교사·학급·과목·요일·교시를 정규화한 SHA-256이며 저장된 레코드 ID와 별개다.

## 알고리즘과 시간 제한

- 배당 행(교사·과목·학급)의 주당 시수를 고정한다. 교사와 학급을 잇는 각 수업을 한 교시에 배정하며, 양 끝점이 이미 점유된 교시는 사용할 수 없다. 빠른 초기화는 빈 교시를 고르거나 두 교시 사이의 교대 경로를 따라 기존 배치를 옮긴다. 옮기는 교사마다 불가 교시를 확인한다.
- 이어서 반복형 백트래킹으로 제약이 강한 배당부터 탐색한다. 같은 배당의 차시는 교시 조합만 열거한다. 남은 가능한 교시 수가 부족하거나 낙관적인 점수 상한도 4위에 미달하면 해당 가지를 건너뛴다. 주간 교시 수를 S, 배당 i의 시수를 hᵢ라 할 때 최악의 완성 배치 탐색 공간은 ∏ C(S,hᵢ)이다. 필수 제약을 만족한 첫 안 이후에도 점수를 개선할 수 있다.
- 후보 채택 전 독립 검증기가 행별 정확한 시수, 교사·학급 교시 중복, 불가 교시 위반을 다시 계산한다. 검증을 통과한 상위 4개만 불변 목록으로 교체한다.
- JVM당 큐 없는 워커 1개를 사용한다. 서버가 검증본 조회를 시작할 때부터 입력 준비·모든 초기화·모든 후보 탐색이 하나의 단조 시계 마감을 공유한다. 60초 중 250ms는 취소와 응답 조립에 남긴다. 워커는 탐색·재배치·검증 중 마감을 확인하고, 호출 측도 남은 시간만 기다린 뒤 인터럽트한다. DB·Redis I/O가 늦게 반환해도 마감 후 솔버를 시작하지 않는다. HTTP 본문 수신·JSON 직렬화·네트워크 전달은 측정된 편성 시간 밖이다.
- 현재 입력 단위는 한 교사·한 통학급·한 과목의 1교시 수업이다. 강의실, 선택 분반·합반, 연강, 교사 간 이동시간은 이 API의 입력 모델에 포함되지 않는다.

## 검증 결과

2026-11-22, Java 17, 단일 탐색 워커에서 합성 주간 시수표로 측정했다. 아래 시간은 메모리에 준비한 입력을 워커에 전달한 때부터 비교 결과를 받을 때까지다. 실학교 엑셀, Redis·DB 왕복, HTTP 전송 시간은 별도다.

| 30학급 · 1,050차시 · 35교시 | 7 | 매회 유효 후보 4개, p50 7ms / p95 7ms |
| 60학급 · 2,100차시 · 35교시 | 7 | 매회 유효 후보 4개, p50 7ms / p95 11ms |

| 12명이 같은 반의 같은 1교시를 희망 | 1 | 실제 60초 제한에서 59.750초에 종료, 유효 후보 4개 유지, 최고 후보 희망 1/12 충족 |

앞 세 행은 미제출 선호와 빈 불가 목록을 사용했다. p95는 7회 소표본의 최근접 순위 기준 최댓값이다. 별도 테스트에서 작은 문제의 완전 열거 결과와 유효해 개수·점수 순위를 대조했다. 입력 검증부터 후보 응답까지의 HTTP 테스트는 저장소 경계를 대역으로 두고 실행했다. 전체 64개 테스트가 통과했다.

성능 테스트는 기존 백엔드 테스트 환경에서 `M2_FULL_BENCHMARK=1 bash gradlew test --tests '*CandidatePerformanceTest' --rerun-tasks`로 재실행할 수 있다. 기본 테스트에는 짧은 마감으로 검증하는 시간 초과·워커 취소·재사용 사례도 포함된다.
